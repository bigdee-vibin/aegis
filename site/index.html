A privacy firewall for the AI era

Aegis is a planned local-first layer that controls what personal and sensitive information reaches AI providers, inspects what comes back, and routes requests between local and cloud models with privacy taking precedence.

Status

Pre-release. Design prototype and early gateway slice. Not a working firewall yet. No protection is claimed.

Do not rely on Aegis to protect any data today. Nothing below has been measured for effectiveness. Status as of 2026-11-17, copied by hand from the repository's own audit, PRD and commit notes; this page does not update itself.

What exists

  • Architecture package: system design, threat model, API contracts, backlog, 20+ decision records (ADRs).
  • PRD v1.0 draft with requirement IDs and a 19-test acceptance suite (on a branch, awaiting owner review).
  • A clickable design board (coded prototype, sample data only).
  • A Rust workspace scaffold and an early gateway slice for blocking secrets (on a branch, not released).
  • A test kit with mock cloud and mock Ollama servers (on a branch).

What is not verified

  • All 19 acceptance tests are recorded as Not started in the PRD. None counts as passed.
  • The gateway slice was run locally once (51 tests, on a scratch copy with different dependency pins that are not in the repo). MSVC build, CI on Windows, macOS and Linux, and cargo-deny are unverified.
  • Detection recall and precision: never measured.
  • Feasibility spikes (encrypted storage, browser Native Messaging, site interception): not run.
  • Accessibility of the design board: contrast measured by script; no assistive-technology audit.

What does not exist

  • A released build, installer or download.
  • A browser extension.
  • A desktop app or credential vault.
  • LOCAL ONLY enforcement, routing, response inspection, reconstruction.
  • Any site or app that is actually protected.

Primary sources: initial audit, PRD draft (section 8, acceptance suite), and the commit notes on the m0-m1-scaffold branch.

How it is designed to work

This is the intended flow from the architecture documents. It describes design intent, not shipped behaviour. Every step below is either unbuilt or unverified.

  1. Your request

    An application or supported browser site sends a prompt, with an API key or personal data possibly inside it.

  2. Local gateway

    A background process on your device receives it first. Applications opt in by pointing their OpenAI-compatible base URL at it.

  3. Inspect

    Deterministic detectors (key formats, private keys, emails, checksums) run first. A small local classifier is planned as a later, optional layer that can only raise severity.

  4. Decide

    Policy picks notify, review or block. Critical secrets are blocked by a mandatory rule no profile can relax.

  5. Review, two approvals

    You see original and proposed text side by side. You approve the change, then separately approve sending that exact text.

  6. Single egress point

    Only content carrying an approval capability may leave. Responses are buffered and inspected before release.

Principles recorded in the design: fail closed when inspection fails; never modify your content without approval; the audit log holds metadata only; no telemetry; LOCAL ONLY never falls back to cloud silently.

Confirmed scope (v1.0 plan)

Taken from the PRD draft's confirmed decisions. A plan, not a commitment of dates.

In scope

  • Individual AI users
  • Local OpenAI-compatible gateway (chat completions first)
  • Chrome-family extension with a local companion
  • Secret and personal-data detection, review, two approvals
  • LOCAL ONLY mode with Ollama
  • Metadata-only audit, zero telemetry
  • Windows, macOS, Linux (as planned in ADR-0020)

Not in v1.0

  • Team or enterprise management
  • A hosted Aegis cloud service
  • Universal website coverage
  • System-wide traffic interception
  • Image and file inspection (blocked on cloud routes instead)
  • Learning engine, token optimiser, desktop-app connectors

Stated limits

  • No protection against malware running as the same OS user
  • No guarantee that every sensitive item is detected
  • Unsupported sites and formats are not inspected
  • Nothing is protected before login or while the background process is stopped

Coverage tiers: what protection would mean

Websites are not under Aegis control, so the design labels coverage per integration instead of claiming blanket protection (ADR-0012). The interface vocabulary is Protected, Partially protected and Not protected. Today every integration is Planned and none is Protected.
